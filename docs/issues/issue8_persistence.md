# Issue #8: Room KMP による登録地点の永続化

## 概要

**登録した地点**の緯度・経度（必要ならラベル）を Room KMP で端末に保存します。  
DB に保存するのは **地点情報だけ** です。天気・予報は保存せず、表示のたびに API から取得します。

アプリを閉じて再度開いたとき、DB から登録地点を読み出し、その座標で天気 API を呼び出して **登録地点の天気や予報を表示する** ことが本 Issue の目標です。

**登録地点** と **現在地** の両方の情報がユーザーから確認できる UI にします（レイアウトの厳密な指定はありません）。永続化の利点（再起動後も「登録した地点」が残り、その地点の天気を再取得できる）が体験として分かる構成にしてください。

> **任意課題**です。Issue #6 で現在地取得ができていることを前提に進めてください。

## この Issue で作る機能（イメージ）


| 種類       | 内容             | データの出どころ                              |
| -------- | -------------- | ------------------------------------- |
| **登録地点** | 登録済みの地点の天気・予報  | Room の **地点情報** → その座標で API 取得        |
| **現在地**  | いま取得した位置の天気・予報 | 位置情報 API → その座標で API 取得（Issue #6 と同様） |


**登録**の操作例: 「この位置を登録」ボタンで、いまの現在地の **緯度・経度（と必要ならラベル）だけ** を DB に保存する。

画面構成（タブ・スクロール・別画面など）は **自由** です。次の 2 点だけ守ってください（[UI の要件](#ui-の要件) 参照）。

1. **登録地点** と **現在地** の両方が、ユーザーから区別して確認できること
2. データがないとき（未登録・取得失敗など）が **分かる表示** であること

## 前提

- Issue #2 の通信と、Issue #4 / #5 の UI が動作していること。
- Issue #6 で **現在地** の取得と、それを使った天気表示ができていること。

## 課題内容

- Room KMP 対応の `androidx.room` を導入する（KSP の設定を含む）。
- **登録地点の地点情報**（緯度・経度、必要ならラベル）を保存する Entity / DAO / Database を `commonMain` に作成する。
- `androidMain` / `iosMain` で `DatabaseBuilder` の `actual` 実装を行う。
- **登録**操作で、現在地の **地点情報だけ** を DB に保存する。
- アプリ起動時に DB から登録地点を読み出し、その座標で API を呼んで **登録地点**の天気・予報を UI に表示する。
- **現在地**は、これまでどおり位置情報から取得した座標で API を呼び、UI で確認できるようにする。

## UI の要件

**レイアウトや画面数の指定はありません。** 次の 2 点を満たせば、実装方法は何でも構いません。

1. **登録地点** と **現在地** の両方が、ユーザーから **区別して確認できる** こと
  - 例: 1 画面の 2 セクション、タブ切り替え、別画面への遷移、見出し付きの縦並び など
2. **データがないことが分かる表示** であること
  - 例: 未登録時は「登録地点は未登録」、現在地の取得失敗時はエラー表示、登録地点の天気取得失敗時はエラー表示

表示の中身（天気 1 件 / 予報リストなど）は Issue #4 の成功表示と同程度でよいです。登録操作（ボタン等）から **地点情報の DB 保存** までつながっていれば十分です。

## データ設計の目安

- **DB に保存するもの**: 地点情報のみ（緯度・経度、必要ならラベル）。**天気・予報は保存しない**。
- **登録地点**は 1 件でよい（複数都市のお気に入りは発展課題）。
- 再起動後は、保存した座標を読み出してから **通信で天気・予報を取得** する。
- オフライン時は登録地点の天気取得は失敗しうる（地点情報だけ DB に残る）。その場合も [UI の要件](#ui-の要件) に沿って状態が分かる表示にすること。

## 編集するファイル


| ファイル                                                     | 内容                     |
| -------------------------------------------------------- | ---------------------- |
| `gradle/libs.versions.toml`                              | Room / KSP のバージョン      |
| `composeApp/build.gradle.kts`                            | KSP プラグイン、各ソースセットの依存関係 |
| `commonMain`（Entity / DAO / Repository / ViewModel / UI） | 地点の登録・読み出し・登録地点／現在地の表示 |


## ヒント

- **なぜ Room か**: メモリだけではアプリ終了後に登録地点が消えます。**再起動後も同じ地点の天気を取りに行く**ために、地点情報を DB に残します。
- **保存と表示の分離**: 登録時は DB へ地点だけ書き込み、表示時は Repository 経由で API 取得する流れにすると分かりやすいです。
- **公式ドキュメントを参照**: Room KMP の対応状況とセットアップ手順は更新が速いため、[Room の KMP ガイド](https://developer.android.com/kotlin/multiplatform/room) の **最新の stable 手順**に従ってください（Issue 本文ではバージョン番号を固定しません）。
- **KSP**: `commonMain` と各プラットフォームターゲット向けに KSP の設定が必要です。ビルドエラーが出たら、公式サンプルと `composeApp/build.gradle.kts` を突き合わせてください。
- **UiState**: `登録地点用` と `現在地用` の状態を分けて持つと UI が整理しやすいです（1 つの sealed class にまとめても構いません）。

## 完了条件

- **登録**操作で、現在地の **地点情報だけ** が DB に保存されること。
- アプリを **完全に終了して再起動** しても、DB から登録地点を読み出し、**その座標で取得した** 天気・予報が **登録地点**として UI で確認できること（通信が可能な状態で確認）。
- **登録地点** と **現在地** の両方が区別して確認でき、データがない場合はそれが分かる表示になっていること。
